# ИТ-Задачи — трекер задач и их решений

Веб-сервис для системного администратора, который помогает отслеживать
выполнение задач и решений этих задач. Работает как «сервис-деск» внутри
небольшой команды:

- **Вы (исполнитель)** создаёте задачи, отмечаете стадию выполнения, пишете,
  как решаете задачу, и прикладываете фото результата.
- **Начальник** создаёт задачи, прикладывает фото проблемы, следит за ходом
  решения и видит результат.
- Всё хранится в одном месте, доступно с любого устройства, обновляется в
  реальном времени.

## Возможности

- 🔐 Вход по логину/паролю (без email), роли: **Начальник**, **Исполнитель**, **Админ**.
- 👥 Админ-панель «Пользователи» — создание учётных записей и смена ролей.
- 📝 Создание задач с описанием, приоритетом и назначением исполнителя.
- 🚦 Стадии: Новая → В работе → Ожидает → Решена / Отменена.
- 💬 «Ход решения» — лента записей о том, как решается задача.
- 📷 Прикрепление фото проблемы и фото решения (с автосжатием).
- 🔍 Фильтры по статусу, поиск, «Мои задачи».
- ⚡ Живое обновление (realtime) — изменения видны сразу всем.
- 🌐 Деплой на GitHub Pages.

## Стек

React 19 + TypeScript + Vite + Tailwind CSS 4 + Supabase (Auth, Postgres,
Storage, Realtime).

## Быстрый старт (локально)

```bash
npm install
cp .env.example .env      # затем впишите свои ключи Supabase (см. ниже)
npm run dev
```

Приложение откроется на `http://localhost:5173`. Пока ключи Supabase не
заполнены, на экране входа будет подсказка по настройке.

Сборка для продакшена:

```bash
npm run build
```

## 1. Настройка Supabase (бесплатно)

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте новый
   проект (организация + регион — любой).
2. В проекте откройте **SQL Editor → New query**, вставьте **весь** файл
   [`supabase/schema.sql`](./supabase/schema.sql) и нажмите **Run**.
   Это создаст таблицы, триггеры, RLS-политики, realtime и хранилище для фото.

   > **Если `schema.sql` уже запускался раньше** (до перехода на вход по
   > логину) — выполните вместо этого миграцию
   > [`supabase/migrations/002_username_login.sql`](./supabase/migrations/002_username_login.sql).
3. Откройте **Project Settings → API** и скопируйте:
   - **Project URL** (например `https://xxxx.supabase.co`)
   - **Publishable key** (начинается с `sb_publishable_...`)
4. Впишите их в `.env` (для локальной разработки):

   ```env
   VITE_SUPABASE_URL=https://xxxx.supabase.co
   VITE_SUPABASE_ANON_KEY=sb_publishable_...
   ```

### Отключить подтверждение email (обязательно)

Вход по логину использует технический email вида `логин@it.local`, на который
невозможно получить письмо. Поэтому подтверждение email **нужно выключить**:

**Authentication → Providers → Email** → выключите **Confirm email**.

### Первый вход и роли

1. **Сделайте себя администратором** — выполните в SQL Editor
   (подставьте свой логин):

   ```sql
   update public.profiles p
   set role = 'admin'
   from auth.users u
   where u.id = p.id
     and split_part(u.email, '@', 1) = 'ваш_логин';
   ```

2. Войдите на сайт под своим логином — появится пункт меню **«Пользователи»**.
   Там вы создаёте учётные записи (логин + пароль + имя + роль) и меняете роли
   без SQL. Роли: **Исполнитель**, **Начальник**, **Админ**.

> Вход — по логину (латиница, 2–32 символа). Внутри логин превращается в
> email `логин@it.local` — реальная почта не используется.

## 2. Деплой на GitHub Pages

1. Создайте репозиторий на GitHub и залейте этот проект (папку `task-tracker`).
2. Настройте **секреты** репозитория
   (**Settings → Secrets and variables → Actions → New repository secret**):

   | Имя секрета              | Значение                               |
   |--------------------------|----------------------------------------|
   | `VITE_SUPABASE_URL`      | Project URL из Supabase                |
   | `VITE_SUPABASE_ANON_KEY` | Publishable key (`sb_publishable_...`) из Supabase |

   > `publishable`-ключ публичный по своей природе — его можно безопасно
   > использовать на клиенте. Доступ к данным ограничен политиками RLS.

3. Включите GitHub Pages:
   **Settings → Pages → Build and deployment → Source** → выберите
   **GitHub Actions**.
4. Отправьте код в ветку `main`:

   ```bash
   git push origin main
   ```

   Сработает workflow [`.github/workflows/deploy.yml`](./.github/workflows/deploy.yml):
   соберёт проект и опубликует его. Сайт будет доступен по адресу
   `https://<ваш-username>.github.io/<repo>/`.

> Проект собирается с `base: './'` и использует `HashRouter`, поэтому ссылки
> выглядят как `.../#/tasks/123`. Это позволяет корректно работать и в корне
> домена, и в подпапке репозитория без настройки сервера.

## Структура проекта

```
src/
  lib/            # Supabase-клиент, типы, константы, хелперы (загрузка фото)
  context/        # AuthContext — авторизация и профиль пользователя
  components/     # Layout, TaskCard, PhotoPicker, Lightbox, UI-примитивы
  pages/          # Login, Dashboard, NewTask, Task, Users (админ-панель)
supabase/
  schema.sql      # Схема БД, RLS, триггеры, realtime, storage-политики
  migrations/     # Миграции (002 — вход по логину)
.github/workflows/
  deploy.yml      # Автодеплой на GitHub Pages
```

## Данные и безопасность

- Все данные (задачи, комментарии, фото) живут в вашем проекте Supabase.
- Фото хранятся в публичном бакете `task-images` (ссылки доступны только тем,
  кто знает URL). При необходимости бакет можно сделать приватным и выдавать
  подписанные ссылки.
- RLS включён на всех таблицах: аутентифицированные пользователи могут читать
  задачи и управлять ими. Если нужно строже разграничить права ролей — это
  делается правкой политик в `schema.sql`.

## Частые вопросы

**Почему GitHub Pages, если нужен «бэкенд»?**
GitHub Pages отдаёт только статику. Роль бэкенда выполняет Supabase
(бесплатный тариф), поэтому сам сайт остаётся статичным и бесплатно хостится
на GitHub Pages.

**Фото занимают место. Что делать?**
Изображения автоматически сжимаются до ~1600px перед загрузкой. Бесплатный
тариф Supabase даёт 1 ГБ хранилища. При нехватке места фото можно чистить
вручную в Supabase Dashboard → Storage.
